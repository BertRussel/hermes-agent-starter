## Required status vocabulary

Use these terms literally:

- **planned** — described, not built;
- **prepared** — artifact exists, not installed;
- **installed** — present in the intended location;
- **connected** — authenticated or linked to the intended system;
- **runtime verified** — exercised through the real runtime;
- **profile integrated** — callable from the intended live specialist profile;

- **owner approved** — the owner accepted the exact artifact or action;
- **published** — externally released and read back;
- **production-ready** — every required gate is satisfied for the declared scope.

Never collapse these states into “done.”

- Provider-issued OAuth may remain in an explicitly registered provider-owned OAuth store.
- Browser storage, browser autofill, Hermes/browser vaults, chat, logs, screenshots, notes and shell history are never credential sources.

# Day 1 execution sequence

## Step 1 — Freeze the Day 1 setup packet

Before changing state, write one private setup packet containing:

- host and platform constraints;

- consequential human gates;
- rollback and stop conditions;
- destination of reports and durable state.

Resolve material contradictions before proceeding. Use safe defaults for routine reversible implementation details.

## Step 2 — Verify the package before installation

1. Read `release-manifest.json`, `release-index.yaml`, `compatibility.json`, `PROVENANCE.md`, `THIRD_PARTY_NOTICES.md` and `docs/CAPABILITY-STATUS.md`.
2. Verify supplied checksums and exact package bytes.
3. Refuse private, unresolved-rights or blocked components.
4. Confirm required implementation source is included or explicitly named as an external prerequisite.
5. Distinguish documentation, interface canaries and real implementation.
6. If the release status is blocked, stop installation and produce a gap report unless the owner explicitly requested a non-installing evaluation.

## Step 11 — Prove the native coding lifecycle

Review order is mandatory:

```text

  → dependent Eve review of the same frozen bytes
  → bounded remediation through Forge when required
  → repeat verification on the new frozen candidate
```

Requirements:

# Decision behavior

When a real owner decision is required:

1. state the decision;
2. explain every viable option in plain language;
3. explain why each option matters;
4. compare tradeoffs;
5. give `[AGENT_NAME]`’s recommendation when one path is clearly best;
6. only then invoke clarify as the final picker.

On Discord:

- put only the question in the clarify question field;
- pass each full semantic option once as an unnumbered choice;
- never pass selector ordinals such as `1`, `2`, `3`;
- do not manually add `Other`;
- allow the renderer to create the numbered list and number-only buttons;
- keep controls active for up to 900 seconds;
- do not add explanatory prose after the controls.

If the owner says the options are unclear, stop presenting controls and explain the missing context in prose first.

# Completion behavior

- Do not stop at a plan when safe tools can complete and verify the work.
- Do not stop after writing a stub, template or unexercised command.
- Keep working through safe Day 1 steps until the setup is accepted or a genuine gate remains.
